# ADP — Acceptance → Anchor → Delta → Prove

Методология: **от репозитория к полному диффу**, не от «идеи фичи» к демо и не к «зелёному lint при недоделанной задаче».

Порядок слоёв обязателен. Skill можно проигнорировать; зелёная команда проекта и явные AC — то, на чём держится сдача.

## Зачем

Типичный провал агента:

- урок / игрушка / костыль вместо вливания в путь;
- узкий «работающий» кусок при неполном ТЗ;
- зелёная команда при мёртвом коде и обходе слоёв;
- ты потом гоняешь круги «всё ли? / качество?».

ADP закрывает это **до сдачи**: полный Acceptance с доказательствами, якорь в репо, оракул проекта, правка своего diff — без меню рефакторинга и без LLM-ревьюера.

## Стек (только в эту сторону)

```text
1. ACCEPTANCE — полный проверяемый список; если запрос размыт → CLARIFY
2. ЯКОРЬ      — существующий путь + сосед в репо
3. ДЕЛЬТА     — изменение относительно якоря, привязка к AC
4. ОРАКУЛ     — команда из project.md или твоя
5. КОД        — все AC, только вдоль якоря
6. CLOSE      — evidence по каждому AC + уборка своего diff
7. PROVE      — оракул зелёный → стоп
```

Нет: «угадай и сделай», «сначала хоть как», «потом ты проверишь», «ревьюер примет».

## Acceptance и Clarify

До любого кода фичи — нумерованный список (AC1…). Покрывает весь запрос, не удобный минимум.  
Out of scope — явно.  
AC готов только если его можно проверить, не спрашивая «а что ты имел в виду?».

**Размытый запрос → цикл Clarify, не реализация:**

1. что неясно;  
2. короткие блокирующие вопросы;  
3. переписать Acceptance;  
4. ещё мутно — снова уточнить.  

Угадывать смысл и писать код **запрещено**. Код только после точного Acceptance.

Сдача без evidence по каждому AC запрещена.

## Якорь

Пути должны существовать (не выдуманы):

- путь в проде;
- 1–3 соседа «как у нас»;
- точка встройки;
- что нельзя плодить параллельно.

Нет якоря → стоп. Greenfield: якорь = форма соседних модулей репо, не tutorial.

## Дельта

Было → станет; точки пути; какой AC куда ложится; как у соседа (ошибки, слой, имена).  
Запреты: не урок, не rewrite подсистемы, не обход якоря, mergeable as-is.

## Оракул

Команда из `.cursor/kits/andreev-sy/cursor-tools/project.md` → Verify → Run these  
(ссылка из корневого `AGENTS.md`), либо команда, которую ты назвал в чате.

Нет команды → стоп (bootstrap или ты). Не выдумывать тесты «для протокола».  
Красный → не сдано. Зелёный один не достаточен без полного Acceptance evidence.

## Close (до/вместе с Prove)

На коде, который агент трогал:

- каждый AC → done + доказательство (путь/символ и/или поведение оракула);
- убрать мёртвое/неиспользованное, что сам ввёл;
- не дублировать то, что уже делает сосед;
- не обходить слой якоря.

Дыры закрывать самому. Не спрашивать пользователя «найти недочёт».

## Форма промпта

Плохо:

> Сделай экспорт пользователей в CSV.

Хорошо:

```text
/andreev-sy-cursor-tools-adp

Якорь: тот же путь, что <сосед / модуль>.
Нужно: <поведение и важные края>.
Нельзя: <параллельный стек, обход, one-off>.
Доказательство: команда из project.md / <твоя команда>.
```

Перед промптом:

1. Где в проекте это живёт?  
2. На что похоже уже сделанное?  
3. Чем докажем влитие?  
4. Что обязательно должно быть в результате (чтобы не урезали)?

## Чеклист

| # | Шаг | Код фичи? |
|---|-----|-----------|
| 1 | Intent | нет |
| 2 | Acceptance точный (иначе Clarify, без кода) | нет |
| 3 | Якорь с путями | нет; иначе STOP |
| 4 | Дельта + map на AC | нет |
| 5 | Оракул назван | нет; иначе STOP |
| 6 | Код всех AC вдоль якоря | да |
| 7 | Evidence + clean diff | да, до сдачи |
| 8 | Оракул green → стоп | — |

## Что не делать

- Тема без места в репо.
- Угадывание при размытом запросе.
- Демо рядом с продом.
- Сдача при неполных AC.
- LLM-ревьюер вместо evidence + оракула.
- После green — ритуал «проверь качество» с пользователем как рабочий флоу.
